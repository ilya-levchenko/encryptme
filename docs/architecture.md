# Архитектура

EncryptMe использует общий React/Vite-интерфейс и две платформенные реализации одного контракта `window.encryptMe`.

```text
React UI
   │
   ├── Electron preload/IPC ── Electron main ── локальные файлы desktop
   │                                      └──── временный HTTP-узел Wi-Fi
   │
   └── Capacitor bridge ────── Web Crypto ───── приватный vault iOS/Android
                              ├──────────────── Wi-Fi sync client
                              └──────────────── BLE CoreBluetooth/GATT
```

## Границы платформ

- `src/App.tsx` отвечает только за состояние интерфейса и вызывает платформенный контракт.
- `electron/preload.cjs` предоставляет минимальный IPC API без доступа UI к Node.js.
- `electron/main.mjs` владеет desktop-сессией и файловой системой.
- `src/platform/` реализует тот же API для iOS, Android и browser development.
- `src/platform/haptics.ts` добавляет единый слой тактильной отдачи через Capacitor Haptics.
- `native/bluetooth-sync/` содержит общий локальный Capacitor-плагин с CoreBluetooth и Android GATT.
- `ios/` и `android/` содержат нативные оболочки и платформенные меры защиты.

## Форматы данных

Контейнер сейфа версии `2` состоит из небольшого зашифрованного индекса и независимо зашифрованных записей. Оба независимых сейфа используют общий случайный KDF-salt, но разные пароли и ключи. Новые сейфы выводят ключ через PBKDF2-HMAC-SHA-256 с 600 000 итераций, который на iOS исполняется нативным Web Crypto. После одного вывода ключа приложение проверяет оба индекса быстрым AES-GCM. Индекс подходящего сейфа расшифровывается сразу, а текст конкретной записи — только при её выборе. Каждая часть использует собственный случайный IV.

У старых профилей общий salt назначается при первом успешном входе. Активный scrypt-сейф атомарно переводится на PBKDF2. Когда пользователь впервые открывает второй сейф, он проходит такую же миграцию; дальнейшие входы с обоими паролями используют один быстрый нативный KDF-вызов.

Сейфы версии `1`, в которых дневник был зашифрован целиком, поддерживаются для чтения. После первого успешного ввода пароля приложение атомарно переводит выбранный сейф в версию `2`; при ошибке записи исходный контейнер остаётся на месте.

Резервная копия содержит профиль и оба уже зашифрованных сейфа, после чего целиком дополнительно шифруется активным паролем. Это позволяет переносить один файл между desktop, iOS и Android без конвертации.

## Синхронизация по Wi‑Fi

Desktop открывает временный HTTP-узел на случайном порту всех локальных интерфейсов. Сеанс живёт пять минут, допускает не более восьми ошибок кода и закрывается после первого успешного обмена. Windows локально строит QR-пакет версии 1 из приватного IPv4-адреса и 12-значного одноразового кода. iOS проверяет схему, версию, адрес и код после нативного сканирования, а затем сразу инициирует обмен. Ручной ввод использует тот же протокол. Сервер не работает в фоне после закрытия сейфа.

По сети передаётся контейнер только активного сейфа. Ответ сервера содержит только зашифрованный контейнер и статистику объединения — расшифрованные данные в HTTP-ответ не включаются. Индекс и записи уже защищены AES-256-GCM; принимающая сторона дополнительно пытается расшифровать индекс текущим ключом, поэтому контейнер другого сейфа отвергается. Настоящий и запасной сейфы не получают общего сетевого идентификатора.

Записи объединяются независимо по времени последнего изменения. Удаления хранятся в зашифрованном индексе как tombstone-маркеры и распространяются между устройствами. После объединения создаётся новый зашифрованный индекс, а неизменившиеся ciphertext-записи копируются без повторного шифрования.

## Синхронизация по Bluetooth

Мобильные устройства используют одинаковый высокоуровневый протокол и нативные central/peripheral роли. BLE-реклама содержит только UUID сервиса и временный случайный номер. Передаваемый зашифрованный сейф дополнительно помещается в AES-GCM-конверт активного ключа с SHA-256, режется на GATT-фрагменты и собирается с проверкой порядка. Сеанс принимает одно соединение, живёт пять минут и останавливается при блокировке или уходе в фон. Слияние выполняется общим модулем `src/platform/sync-merge.ts`.

Browser fallback предназначен только для разработки интерфейса и хранит зашифрованные контейнеры в `localStorage`; production desktop использует Electron, а iOS/Android — Capacitor Filesystem.

Стеклянные поверхности реализованы как progressive enhancement через системное размытие WebKit. Настоящий `UIGlassEffect` относится к нативным UIKit-контролам и не применяется напрямую к DOM внутри `WKWebView`, поэтому интерфейс сохраняет безопасный непрозрачный fallback на старых iOS.
